# ADR-001: Архітектурний рефакторинг системи абонементів фітнес-клубу за GRASP

## Статус
Прийнято (Accepted)

## Контекст
У вихідному коді (`LegacyFitnessService`) вся бізнес-логіка обчислення вартості абонементу (знижки, тарифи, персональні тренери) була зосереджена в процедурному сервісі, а класи `Member`, `MembershipPlan` та `Subscription` містили лише публічні поля без поведінки (Anemic Domain Model). Це призводило до високого зачеплення (High Coupling), порушення інкапсуляції та складності внесення змін у бізнес-правила.

## Рішення
1. **Information Expert**: Перенести обчислення базової вартості, знижок та підсумкової ціни безпосередньо в доменну сутність `Subscription` та об'єкти-значення (`MembershipPlan`), які володіють цими даними.
2. **Creator**: Покласти відповідальність за створення екземплярів `Subscription` на статичні фабричні методи або спеціалізовані фабрики, що гарантують валідний стан з імутабельними властивостями.
3. **Controller & Pure Fabrication**: Відокремити консольне введення-виведення від бізнес-логіки за допомогою контролера `SubscriptionController` та виділити допоміжні сервіси (`SubscriptionRepository`, `NotificationService`, `ConsoleCommandParser`).
4. **Polymorphism & Protected Variations**: Замінити процедурні розгалуження (`if-else` за типами `Day`, `Full`, `VIP`) на поліморфну ієрархію розрахунку тарифів (`IMembershipPricingStrategy`).

## Наслідки
### Позитивні:
- Знижено показник `CBO` (Coupling Between Objects) для ключових класів до цільового значення $\le 4$.
- Підвищено згуртованість (`LCOM4 = 1`) для доменних сутностей.
- Захищено інкапсуляцію стану завдяки використанню `private set` / імутабельності.
- Код став гнучким до додавання нових типів абонементів без зміни існуючої логіки.

### Негативні / Компроміси:
- Збільшилась кількість класів за рахунок введення інтерфейсів, стратегій та фабрик.
